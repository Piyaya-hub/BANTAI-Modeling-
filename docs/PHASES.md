# Development phases

Every transition requires explicit project-owner authorization. Acceptance criteria define evidence to review; listing a phase does not authorize it. Later phases are conditional and may be revised or declined.

| Phase | Work | Acceptance criteria |
| --- | --- | --- |
| 0 — Foundation documentation | Document scope, inference design, decisions, validation, and tool collaboration rules. | All eight required Markdown files exist; local references resolve; trash-only AI modelling scope, three categories, multi-region requirement, GroundingDINO-T starting model, and prompt-first strategy are consistent; approved decisions and proposals are separate; unknowns are explicit; no model code, ML dependencies, or downloaded models are added; `.gitignore` is preserved; documentation is committed on a focused branch and offered for review. |
| 1 — Evaluation preparation | After authorization, verify the exact GroundingDINO-T implementation, checkpoint source/revision, configuration, dependency/runtime compatibility, and RTX 2080 Super suitability; prepare images, annotations, prompts, data handling, and reproducibility protocol. No mandatory spatial grouping implementation. | Selection, provenance, license, environment requirements, input/output contract, dataset rights, three-category annotation/membership/overlap rules, multi-region output contract, separate/combined prompt experiment design, threshold-selection procedure, object-level and region-level metrics, and owner-approved success criteria are recorded. Any required environment setup is verified. No unresolved prerequisite needed for evaluation remains. |
| 2 — Still-image evaluation | After authorization, implement and evaluate pretrained GroundingDINO-T direct prompting on still images for all three categories and mixed spatial conditions. | Actual execution evidence is retained; input failures, empty outputs, and box coordinates are checked; annotated evaluation reports metrics under the recorded protocol, separate object-level and region-level performance, mixed-category/multi-region cases, representative failures, timing/resource observations, and limitations. Prompt/threshold exploration remains separate from held-out evaluation. Reproduction instructions work. Report unmet success criteria honestly; phase review may recommend revision rather than progression. |
| 3 — Evidence-based next-step decision | Review evaluation findings before selecting further work. | Owner records whether to retain direct prompting, improve prompts/thresholds, investigate DBSCAN or other grouping, investigate hybrid detection, consider alternative models/fine-tuning, revise evaluation, or stop. Any approved experiment has its own scope, acceptance criteria, resource/data requirements, and authorization before execution. |
| 4 — Conditional model improvement and integration readiness | Only approved model improvements, reproducible inference components, packaging, an agreed output schema, and integration documentation; no full-stack application development. | Before implementation, each selected modelling deliverable has an approved design, data policy, measurable acceptance criteria, and validation plan. Outputs and documentation demonstrate integration readiness without building application APIs, incident management, databases, or hotspot ranking here. Completion requires recorded evidence against those capability-specific criteria and owner review; none is claimed complete now. |
